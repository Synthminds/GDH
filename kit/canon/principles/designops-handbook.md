# DesignOps Handbook (InVision DesignBetter)

Book id `designops-handbook`, id prefix `P-OPS`. 22 principles, 6 of them gates. The machine-readable copy is in [principles.json](../principles.json); this file matches it word for word.

Gates: P-OPS-05, P-OPS-06, P-OPS-13, P-OPS-17, P-OPS-21, P-OPS-22.
Every other principle is a default. Query them with the `design-principles` skill.

## Chapter 1: Introducing DesignOps

**P-OPS-01 Let work be torn down.** Before refining, let a direction be broken apart and rebuilt at least once, and do not polish the first assembly. Test: The record shows a rebuilt variant of a direction before that direction was refined.

**P-OPS-02 Options side by side.** Show options together in one view, such as a board, contact sheet or comparison page, never one at a time. Test: Each option round is presented in a single side-by-side view.

**P-OPS-03 Judge by need, not schedule.** Mark the delivery checklist pass or fail on at least one criterion tied to the stated user need, not only on whether it shipped on time. Test: The delivery checklist has a user-need criterion marked pass or fail with evidence.

**P-OPS-04 Choose tools for craft first.** Pick a tool for what it does well for the design task, and treat already connected only as a tiebreaker. Test: Each tool choice in the plan names the design task it does well.

## Chapter 2: DesignOps scenarios and models

**P-OPS-05 Scope every review up front.** Open every review artifact with four lines: the feedback wanted, from whom, what feedback is not useful now, and what is locked. Test: Every review artifact begins with the four-line scope block.

**P-OPS-06 Grow a locked list.** Declare which elements are final at each gate, and answer a change request against a locked item with an explicit reopen question and its cost. Test: The locked list grows at each gate, and every change to a locked item follows a recorded reopen decision.

**P-OPS-07 One decider per aspect.** Name one final decision maker for each aspect of the output, such as brand, copy and technical, and hear everyone else as input. Test: The brief names exactly one decider for each aspect.

**P-OPS-08 Feedback type follows stage.** Tell reviewers which kind of feedback fits each stage, such as direction at concept and detail at refinement. Test: Each stage in the plan lists its allowed feedback types.

**P-OPS-09 Force a strict ranking.** Rank deliverables in strict order with no ties at the top, and refuse an everything-is-urgent list. Test: A multi-deliverable plan carries a strict order with no shared first place.

**P-OPS-10 Light path for small work.** Scale process to the job: run a light path for a single small asset and the full path for a brand or product, and record which one and why. Test: The project record states light or full path with a reason.

**P-OPS-11 Restate and challenge the request.** At intake, restate the problem in your own words and raise at least one challenge or question about the request itself. Test: The intake output holds a restatement and at least one challenge to the request.

**P-OPS-12 Spare the maker bookkeeping.** Do the filing, naming, status and license tracking yourself and never ask the user to do bookkeeping the harness can do. Test: The session contains no request that the user file, name or track something the harness could.

## Chapter 3: Putting DesignOps into play

**P-OPS-13 Design QA before launch.** Run a dated design QA against the spec and the design system before any launch, and record the approver and the version approved. Test: Each launch has a dated QA result and an approval naming approver and version.

**P-OPS-14 Visual status, not prose.** Send status updates that show the current artifact for each active item, plus progress, blockers and the decisions needed. Test: Each status update holds a visual per active item and a decisions-needed line.

**P-OPS-15 End critique with owned actions.** Close every critique with a numbered action list in which each action has an owner. Test: Each critique log ends with numbered, owned actions.

**P-OPS-16 Enforce a naming convention.** Fix a file naming convention and folder structure for the project and check every file against it. Test: A naming check over the project files reports zero violations.

## Chapter 4: Team coordination

**P-OPS-17 Record every decision path.** Log each direction change with the options considered, the choice and the reason. Test: Every direction change in the record lists options, choice and reason.

**P-OPS-18 Drop check-ins that change nothing.** Review each recurring check-in or ritual and remove the ones that never changed a decision. Test: The retrospective records whether each recurring check-in changed a decision.

## Chapter 5: ResearchOps

**P-OPS-19 Search past research first.** Search the project's research and prior work for the question before running any new research, and log the search. Test: Each new research call is preceded by a logged search of existing material.

**P-OPS-20 Insights apart from data.** Write insights as their own file, each linked to the observations that support it. Test: An insights file exists and every insight links to its supporting items.

**P-OPS-21 Track licenses, spend and fallbacks.** Keep each tool's license terms, cost model, approval rule and fallback in the catalog, and get the user's approval before any spend. Test: No spend in the project log lacks an approval or a ceiling that covers it.

**P-OPS-22 Consent for real people.** Record consent or a license for every asset that shows a real person's face, voice or likeness before it is used. Test: Every asset showing a real person has a consent or license note in the manifest.
